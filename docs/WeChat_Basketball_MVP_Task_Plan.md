# 微信篮球进球剪辑助手：小文件版任务计划

版本：v0.1  
日期：2026-11-25  
用途：首版开发范围、任务拆分与验收依据。

## 1. 首版目标

用户在微信客服会话中直接发送小视频，系统自动识别进球并生成集锦，客服将剪辑后的视频直接发送回原会话。

首版以跑通真实微信闭环为目标。优先采用现有 Basketball Highlight Editor 项目的 Python 识别流程和 FFmpeg 剪辑能力，不依赖 Flutter 界面操作。

## 2. 范围与边界

### 本版包含

- 微信客服接收视频消息、下载素材、发送视频。
- 固定机位、单个篮筐清晰可见的视频分析。
- YOLO 检测篮球和篮筐，结合轨迹、篮网运动及穿筐复核筛选进球。
- 根据进球时间点截取原视频，按时间顺序合成 MP4。
- 后台排队、任务状态、失败反馈、有限重试和临时文件清理。
- 成片大小控制，必要时压缩或拆分回传。

### 本版暂不包含

- 数 GB 整场录像上传、分块上传和断点续传。
- 网页上传页、结果领取页、小程序。
- Flutter 桌面或手机客户端改造。
- 面向用户的人工审核界面、球员识别和按球员生成集锦。
- 对全场双篮筐、频繁切镜头、严重遮挡等场景的效果保证。

### 必须实测的渠道约束

“小文件”暂不预设固定 MB 上限。接收原片和回传视频是两条不同链路，分别确认目标账号支持的消息类型、可下载素材、格式、大小限制及回复条件。

优先验证用户以视频消息发送；若要支持将 MP4 作为文件附件发送，需要另行验证消息接收和下载能力，不能默认两者相同。

历史讨论中的 10 MB 不作为本版已确认参数，正式阈值以目标接口的当前文档和真机测试为准。

## 3. 用户流程

1. 用户给微信客服发送视频。
2. 后台接收消息，去重后创建任务，并在渠道允许时回复“已收到，正在处理”。
3. 后台下载视频，检查文件大小、时长、编码及可解码性。
4. 任务进入队列，执行进球识别与复核。
5. 根据可靠进球时间点生成剪辑，检查成片体积与可播放性。
6. 上传成片素材，通过原客服会话发送给原用户。
7. 保存投递结果；达到保留期限后清理原片和中间文件。

例外：未发现可靠进球时回复“未识别到可确认的进球”；处理失败或格式不支持时给出明确反馈，不生成空视频。

## 4. 实现任务与验收标准

| 编号 | 任务 | 主要工作 | 验收标准 |
|---|---|---|---|
| T1 | 微信收发接入 | 准备客服账号、凭证和回调；完成校验、验签与解密；接收消息、下载素材、上传素材、发送视频 | 手机发送测试视频，后台下载成功，并原样发回同一会话 |
| T2 | 现有引擎验证 | 配置 Python、模型权重、FFmpeg；用目标录像运行识别；核对进球时间点 | 能独立运行并输出候选事件；记录误检、漏检、耗时和设备配置 |
| T3 | 引擎封装 | 整理无需 GUI 的调用入口；明确输入视频、分析区域、剪辑参数和输出结构 | 一条命令完成识别与剪辑，返回事件列表和有效 MP4 |
| T4 | 后台任务管理 | 建立任务记录、排队 worker 和分阶段状态；回调与耗时处理分离 | 回调不等待视频处理完成；任务有状态可查，异常不会静默丢失 |
| T5 | 成片适配 | 设置片段范围、编码和码率；检测大小；必要时压缩或拆分 | 每个发送文件满足实测上限，手机微信内可以播放 |
| T6 | 自动交付 | 将用户、客服账号、原消息与任务关联；处理完成后发送成片并记录结果 | 用户无需额外操作即可收到自己的集锦，不串用户或会话 |
| T7 | 异常与清理 | 重复消息去重；处理无进球、损坏文件、模型失败、发送失败；有限重试与过期清理 | 不重复创建任务；正常重试不重复发送；失败有记录和反馈 |
| T8 | 端到端验收 | 真实微信账号、手机和目标录像测试；覆盖正常与异常路径 | 从发送原片到收到可播放集锦全程跑通，并形成验收记录 |

建议执行顺序：先完成 T1；T2、T3 验证引擎；随后接入 T4—T6；最后完成 T7、T8。

## 5. 识别与剪辑方案

### 识别流程

1. 自动寻找篮筐，生成分析区域；失败时提示本段无法自动处理，并记录原因。
2. 生成低分辨率代理视频，粗扫篮球与篮筐位置。
3. 根据球从筐上方到筐下方的运动筛选疑似事件。
4. 回到原视频，在候选附近精扫并关联轨迹。
5. 使用穿筐、继续下落、反弹、侧向离开、网动等证据复核。
6. 合并重复事件，输出可靠进球与不确定候选。

首版只将复核通过的进球纳入自动成片。不确定候选留在后台，便于误差分析。这一选择会牺牲部分召回率，必须统计真实进球被漏掉的情况。

注意：现有应用保留了人工审核环节。封装时必须明确筛选规则，不能把“未被排除”的候选全部当成“确认进球”。

### 剪辑流程

- 根据事件时间生成起止区间，限制在原视频有效时长内。
- 可先试进球前 5 秒、后 2 秒；作为配置项保留，最终根据目标录像调整。
- 使用原视频导出，代理视频仅用于分析。
- 合并重叠区间，按时间顺序拼接。
- 使用兼容微信播放的编码配置，并以真机结果确认。
- 成片过大时先调整码率；仍不满足限制时，按片段边界拆成多条，并标明序号。

## 6. 最小技术栈

| 模块 | 首版选择 | 用途 |
|---|---|---|
| 微信接入与业务接口 | Python + FastAPI | 回调校验、消息处理、任务创建与查询 |
| 进球检测 | YOLO + OpenCV + NumPy | 球与筐检测、抽帧、轨迹及运动分析 |
| 推理运行时 | PyTorch 或 ONNX Runtime | 根据服务器设备与模型格式选择 |
| 视频处理 | FFmpeg + FFprobe | 元数据检查、截取、转码与合并 |
| 后台任务 | 独立 worker + 任务队列 | 执行耗时任务；具体队列实现按部署环境确定 |
| 状态存储 | SQLite | 用户关联、任务阶段、事件及投递结果 |
| 临时文件 | 服务器本地目录 | 原片、中间产物和成片，按任务隔离 |
| 外部入口 | 稳定的公网 HTTPS 地址 | 接收微信回调；可先验证内网穿透方案 |

首版单机、小规模排队执行即可。无需为了微信版本移植 Flutter 界面或移动端 Rust 引擎，也暂不需要对象存储。

## 7. 任务状态和记录

处理阶段：received → downloading → validating → queued → analyzing → editing → ready。

投递状态单独记录：pending → sending → sent，或 failed。处理成功但发送失败时，只重试发送，不重新识别和剪辑。

至少记录：任务 ID、客服账号与用户标识、原消息 ID、去重键、文件路径与元数据、进球事件及置信证据、处理阶段、错误信息、成片路径、投递状态、时间戳、重试次数。

对外调用超时可能造成“实际已发送，但后台未收到成功响应”。遇到这种状态应先依据渠道能力核对，避免无条件重复发送。

## 8. 三个里程碑

### M1：微信原样收发

完成回调接入、消息接收、下载、上传及回传；确认输入和输出的实际限制。

验收：手机发送短视频，能够在原会话收到回传视频并播放。

### M2：微信固定片段剪辑

在 M1 基础上加入后台任务和 FFmpeg，暂时使用固定时间段，例如截取前 10 秒；原片更短时取有效范围。

验收：客服返回的是正确截取的片段，回调不被处理过程阻塞。

### M3：自动进球集锦

接入 YOLO 检测、轨迹复核和自动筛选，按可靠进球时间点生成集锦；补齐异常反馈和文件清理。

验收：用户发送视频后，收到按时间排序的进球集锦；无可靠进球或失败时收到明确说明。

## 9. 验收样本与指标

测试样本至少覆盖：清晰进球、明显未进、篮筐前方落球、遮挡、不确定事件、无进球、无篮筐、文件损坏、输入超限、成片需压缩或拆分、重复消息、处理失败、回传失败。

记录指标：

- 进球精确率：正确识别进球数 / 系统识别进球数。
- 进球召回率：正确识别进球数 / 人工标注真实进球数。
- 片段完整性：是否包含所需的出手与命中过程。
- 分阶段耗时：下载、解码与代理生成、识别、剪辑、上传及回传。
- 端到端成功率和回传成功率。
- 原片与成片大小、压缩或拆分结果。

准确率和耗时目标在基线实验后确定，不将仓库宣传或个别样本表现当作本项目保证。

## 10. 开发前待确认项

- 目标微信客服账号是否具备所需接口权限。
- 视频消息与文件附件分别能否收取及下载。
- 收发素材的格式、大小、有效期，以及会话回复条件。
- 目标服务器能否运行模型和 FFmpeg，临时磁盘空间及处理耗时是否合适。
- 可用的模型权重来源与依赖授权边界。
- 自动定位篮筐在目标视频上的成功率，以及无需人工干预的可用程度。

以上待确认项以当前官方文档、目标账号真机测试和本地基线实验为准。本文是开发任务计划，不代表微信能力与识别效果已经验证。
